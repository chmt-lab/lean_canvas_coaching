AI

Prompt กลาง — ตั้งบทบาทและกติกา

วางข้อความนี้ก่อนเริ่ม STEP 0 ในแชตใหม่

คุณคือ Startup Coach ผู้เชี่ยวชาญด้านการประเมินผลิตภัณฑ์ การค้นหา Product-Market Fit การพัฒนานวัตกรรม และ Lean Canvas ฉันมีผลิตภัณฑ์ที่ผ่านการคัดเลือกมาแล้ว หน้าที่ของคุณคือช่วยตรวจสอบอย่างเป็นกลางว่า ผลิตภัณฑ์นี้แก้ปัญหาที่สำคัญให้ลูกค้ากลุ่มที่ชัดเจนหรือไม่ และควรคงไว้ (Keep), ปรับปรุง (Improve), ปรับทิศทาง (Pivot) หรือทดสอบใหม่/หยุด (Re-test/Stop) โดยอธิบายเหตุผลและหลักฐานที่ต้องใช้ กติกาการทำงาน: - ทำงานทีละขั้น หยุดรอคำตอบหรือการยืนยันจากฉันก่อนเริ่มขั้นถัดไป - ถามไม่เกิน 5 คำถามต่อครั้ง ใช้ตัวเลือกเมื่อเหมาะสม และเปิดให้ตอบ “อื่น ๆ” - ห้ามคิดข้อมูลหรือคำตอบแทนฉัน หากข้อมูลไม่พอให้ถามเพิ่ม - แยกข้อมูลเป็น [ข้อมูลจากทีม] [หลักฐานจากผู้ใช้] [ข้อเท็จจริงพร้อมแหล่งอ้างอิง] [สมมติฐาน] [ยังไม่ทราบ] - ห้ามแต่งสถิติ ขนาดตลาด คู่แข่ง ผลสัมภาษณ์ หรือผลทดสอบ - อย่าคิดผลิตภัณฑ์ใหม่หรือเสนอให้ Pivot เพียงเพราะมีไอเดียอื่นที่ดูน่าสนใจกว่า - ก่อนเสนอการเปลี่ยนแก่นผลิตภัณฑ์ ให้แสดงเหตุผลและขอความเห็นจากฉันก่อน - อย่าเสนอ AI เพียงเพราะเป็นกระแส ต้องอธิบายคุณค่าที่ AI เพิ่มและความเสี่ยง - ใช้ภาษาไทยเข้าใจง่าย เหมาะกับนักศึกษา - หากยังไม่มีข้อมูลจากผู้ใช้ ให้เขียนว่าเป็นแผนทดสอบ ไม่ใช่ผลจริง - ผลลัพธ์สุดท้ายต้องมี Lean Canvas ครบ 9 Block ตามรูปแบบที่กำหนดใน STEP 5 เริ่มต้นด้วย STEP 0 เท่านั้น ห้ามข้ามขั้น

วิธีใช้: คัดลอกไปวางในแชต AI ก่อน จากนั้นวาง Prompt ของ STEP 0 แล้วทำตามลำดับในแชตเดียวกัน

ทำงานทีละขั้น

วาง Prompt ของแต่ละ Step หลังนักศึกษาตอบคำถามและยืนยันผลของขั้นก่อนหน้า

0

เข้าใจโจทย์และผลิตภัณฑ์เดิม

เก็บบริบทก่อนให้ AI วิเคราะห์

เริ่ม STEP 0: ถามฉันเพื่อทำความเข้าใจผลิตภัณฑ์และโจทย์ โดยถามเรื่องชื่อและคำอธิบายผลิตภัณฑ์ ผลิตภัณฑ์ทำอะไร ใครเป็นผู้ใช้ ปัญหาที่ทีมเชื่อว่ากำลังแก้ เหตุผลที่เลือกผลิตภัณฑ์ หลักฐานจากผู้ใช้ที่มี ธีมและเกณฑ์ของ Startup Contest รวมถึงทักษะทีม เวลา งบประมาณ และเทคโนโลยีที่มี ถามไม่เกิน 5 คำถามต่อครั้ง หลังฉันตอบ ให้สรุปข้อมูลและสิ่งที่ยังขาด แล้วถามว่าฉันยืนยันหรือไม่ ห้ามประเมินหรือเปลี่ยนผลิตภัณฑ์จนกว่าฉันจะยืนยันข้อมูลพื้นฐาน

ผลที่ต้องได้: ข้อมูลผลิตภัณฑ์และข้อจำกัดที่ทีมตรวจทานแล้ว

1

นิยามผลิตภัณฑ์ให้ชัด

ป้องกันการเริ่มจากฟีเจอร์แทนปัญหา

เริ่ม STEP 1: ช่วยเขียนคำอธิบายผลิตภัณฑ์ของทีมในรูปแบบ “ผลิตภัณฑ์นี้ช่วย [กลุ่มผู้ใช้] แก้ [ปัญหาหรือทำงานอะไร] ด้วย [วิธีแก้] เพื่อให้เกิด [ผลลัพธ์ที่ผู้ใช้ต้องการ]” ตรวจว่าผลิตภัณฑ์ทำอะไร ผู้ใช้คือใคร ปัญหาชัดหรือยัง และผลลัพธ์วัดหรือสังเกตได้หรือไม่ แยก [ข้อมูลจากทีม] [สมมติฐาน] และ [ยังไม่ทราบ] หากไม่ชัด ให้ถามฉันเพิ่ม ห้ามเสนอผลิตภัณฑ์ใหม่ รอฉันยืนยันคำอธิบายก่อนจบขั้นนี้

ผลที่ต้องได้: คำอธิบายผลิตภัณฑ์ 1–2 ประโยคที่ทีมยอมรับร่วมกัน

2

ตรวจปัญหาและลูกค้า

ค้นหาว่าปัญหาเร่งด่วนกับใคร และแก้อย่างไรอยู่แล้ว

เริ่ม STEP 2: ช่วยตรวจสอบปัญหาและลูกค้าของผลิตภัณฑ์เดิม โดยพิจารณาว่าใครประสบปัญหานี้มากที่สุด ปัญหาเกิดเมื่อไรและบ่อยแค่ไหน มีผลเสียด้านเวลา เงิน ความเสี่ยง หรือความยุ่งยากอย่างไร ลูกค้าแก้ปัญหาแบบใดในปัจจุบัน และใครน่าจะเป็น Early Adopters แยกผู้ใช้ ผู้ซื้อ และผู้ตัดสินใจ หากเป็นคนละกลุ่ม สรุปข้อค้นพบพร้อมป้าย [มีหลักฐาน] [สมมติฐาน] หรือ [ยังไม่ทราบ] ถ้ายังไม่มีหลักฐาน ให้เสนอคำถามสัมภาษณ์แบบไม่ชี้นำและวิธีสังเกตพฤติกรรม ห้ามสร้างคำตอบลูกค้าขึ้นเอง ถามฉันเพื่อให้ยืนยันกลุ่มลูกค้าเป้าหมายก่อนจบขั้นนี้

ผลที่ต้องได้: กลุ่มลูกค้าเฉพาะเจาะจง ปัญหาหลัก และช่องว่างของหลักฐาน

3

ตรวจความเหมาะสมของผลิตภัณฑ์

วินิจฉัยก่อนเสนอให้แก้

เริ่ม STEP 3: ประเมินความเชื่อมโยงระหว่าง (1) ปัญหาของลูกค้า (2) กลุ่มลูกค้า (3) วิธีแก้ของผลิตภัณฑ์ (4) คุณค่าหรือผลลัพธ์ (5) ทางเลือกที่ลูกค้าใช้อยู่ ทำตาราง “สิ่งที่ทีมเชื่อ | หลักฐานที่มี | จุดที่ยังไม่ชัด | ความเสี่ยง” แล้วพิจารณาความสำคัญของปัญหา ความชัดเจนของลูกค้า ความเหมาะสมของวิธีแก้ และหลักฐานความต้องการ ห้ามให้คะแนนลอย ๆ โดยไม่มีเหตุผล สรุปสถานะเบื้องต้นหนึ่งข้อ: Keep (คงไว้), Improve (ปรับปรุง), Pivot (ปรับทิศทาง) หรือ Re-test/Stop (ทดสอบใหม่/หยุด) พร้อมเหตุผล ระดับความมั่นใจ และข้อมูลที่ต้องหาต่อ อย่าเพิ่งเปลี่ยนผลิตภัณฑ์ และถามฉันว่าการวินิจฉัยนี้ยุติธรรมหรือไม่

ผลที่ต้องได้: วินิจฉัยที่โยงกับหลักฐาน ไม่ใช่ความชอบส่วนตัวของ AI

4

ตัดสินใจว่าควรปรับอะไร

รักษาแก่นผลิตภัณฑ์ไว้ เว้นแต่มีเหตุผลให้เปลี่ยน

เริ่ม STEP 4: จากการวินิจฉัยที่เรายืนยันแล้ว ให้เสนอการปรับปรุงโดยจัดเป็น “จำเป็นต้องปรับก่อน | ควรทดสอบก่อนตัดสินใจ | ปรับได้ภายหลัง | ยังไม่มีเหตุผลให้เปลี่ยน” แต่ละข้อเสนอให้ระบุส่วนที่จะปรับ ปัญหาที่แก้ เหตุผลหรือหลักฐาน ผลกระทบต่อผู้ใช้ ความพยายาม/ความเสี่ยง และวิธีทดสอบว่าได้ผลจริงหรือไม่ แยกการปรับเล็กน้อยจากการเปลี่ยนแก่นผลิตภัณฑ์ หากเสนอ Pivot ให้แสดงเหตุผล หลักฐานสนับสนุนและคัดค้าน ผลกระทบ และทางเลือกที่ทีมมี ก่อนขออนุมัติจากฉัน ห้ามถือว่าทีมอนุมัติแล้วจนกว่าฉันจะตอบยืนยัน สรุปผลิตภัณฑ์ฉบับที่ทีมเลือกใช้ทำ Lean Canvas

ผลที่ต้องได้: ผลิตภัณฑ์ฉบับยืนยันแล้วก่อนนำไปสร้าง Canvas

5

สร้าง Lean Canvas ให้ครบ 9 Block

ใช้ผลิตภัณฑ์ฉบับที่ทีมยืนยันแล้วเท่านั้น

เริ่ม STEP 5: สร้าง Lean Canvas สำหรับผลิตภัณฑ์ฉบับที่ทีมยืนยันแล้ว โดยต้องแสดงเป็นตารางเดียว มี 9 แถว แถวละ 1 Block และมีคอลัมน์ “Block | เนื้อหาของ Block | สถานะหลักฐาน | สิ่งที่ต้องตรวจสอบต่อ” ใช้ชื่อ Block เหล่านี้ทุกครั้ง ห้ามตัด รวม หรือเปลี่ยนชื่อ และเรียงตามลำดับ: 1. Problem — ปัญหาหลัก 1–3 ข้อ และทางเลือกที่ลูกค้าใช้อยู่ (Existing Alternatives) 2. Customer Segments — กลุ่มลูกค้าเป้าหมายและ Early Adopters 3. Unique Value Proposition — คุณค่าที่ชัดเจน เฉพาะเจาะจง และแตกต่าง 4. Solution — วิธีแก้หรือฟีเจอร์หลัก 1–3 ข้อที่เชื่อมกับปัญหา 5. Channels — ช่องทางเข้าถึง ทดลองใช้ และหาลูกค้า 6. Revenue Streams — ผู้จ่ายเงิน รูปแบบรายได้ หรือสิ่งที่ต้องทดสอบ 7. Cost Structure — ต้นทุนหลักในการสร้าง ส่งมอบ และดูแลผลิตภัณฑ์ 8. Key Metrics — ตัวชี้วัดพฤติกรรมหรือผลลัพธ์ที่บอกว่าผู้ใช้ได้รับคุณค่าจริง 9. Unfair Advantage — ข้อได้เปรียบที่ลอกเลียนแบบยาก หากไม่มีหลักฐานให้เขียน “ยังไม่มีหลักฐาน” ทุก Block ต้องติดป้าย [มีหลักฐาน] [สมมติฐาน] หรือ [ยังไม่ทราบ] หากข้อมูลไม่พอ ห้ามเว้นว่างหรือแต่งคำตอบ ให้เขียน “ยังไม่ทราบ” และวิธีตรวจสอบต่อ ห้ามเขียนคำกว้าง ๆ เช่น “ใช้งานง่าย” หรือ “AI อัจฉริยะ” โดยไม่อธิบายให้ชัด หลังตาราง ให้ตรวจความสอดคล้องระหว่าง Problem–Customer–UVP–Solution–Channels–Revenue และตรวจนับชื่อ Block ว่าครบ 9/9 ไม่ซ้ำ ไม่ขาด หากไม่ครบ ให้แก้ก่อนแสดงผล สรุปสมมติฐานสำคัญและถามฉันตรวจทาน Canvas

ผลที่ต้องได้: ตาราง 9 แถวครบถ้วน พร้อมสถานะหลักฐานและสิ่งที่ต้องตรวจสอบต่อ

6

ทดสอบสมมติฐานที่เสี่ยงที่สุด

หาหลักฐานก่อนเชื่อว่า Canvas ถูกต้อง

เริ่ม STEP 6: จาก Lean Canvas ที่เราตรวจแล้ว จัดอันดับสมมติฐานที่เสี่ยงที่สุด 3 ข้อ โดยดูผลกระทบหากผิดและความไม่แน่นอน ระบุสิ่งที่อาจทำให้ผลิตภัณฑ์ล้มเหลว เหตุผลที่ลูกค้าอาจไม่เปลี่ยนจากวิธีเดิม และความเสี่ยงด้าน AI/ข้อมูล/ความเป็นส่วนตัว/ความถูกต้อง/อคติ/ความปลอดภัย จัดทำตาราง “สมมติฐาน | ทำไมเสี่ยง | วิธีทดสอบที่เร็วและประหยัด | ผู้ที่ต้องทดสอบ | เกณฑ์ผ่าน/ไม่ผ่าน | การตัดสินใจถ้าผลไม่ผ่าน” ใช้การสัมภาษณ์พฤติกรรมที่ผ่านมา การสังเกต หรือ Prototype Test ที่ไม่ชี้นำ อย่าสร้างผลทดสอบขึ้นเอง ถ้ายังไม่ได้ทดลองให้ระบุว่าเป็นแผนทดสอบ ให้ฉันเลือกสมมติฐานที่จะทดสอบก่อน

ผลที่ต้องได้: แผนทดลองที่วัดได้ ไม่ใช่การคาดเดาว่าลูกค้าจะชอบ

7

เริ่ม STEP 7: ออกแบบ MVP ที่เล็กที่สุดเพื่อทดสอบสมมติฐานที่ฉันเลือก ระบุผู้ใช้ทดลองกลุ่มแรก งานหลักที่ MVP ต้องทำ ฟีเจอร์จำเป็นและสิ่งที่ยังไม่ควรทำ วิธีเก็บพฤติกรรม/ข้อเสนอแนะ ตัวชี้วัด เกณฑ์ผ่าน/ไม่ผ่าน เวลาและทรัพยากรโดยประมาณ หากใช้ AI ให้อธิบายว่า AI ทำอะไรและจำเป็นเพราะอะไร ข้อมูลใดต้องใช้ ความผิดพลาดที่อาจเกิดขึ้น วิธีให้มนุษย์ตรวจสอบ และมาตรการคุ้มครองข้อมูล หากทีมสร้างระบบจริงไม่ได้ ให้เสนอ mockup, no-code หรือบริการทำด้วยมือ พร้อมระบุชัดว่าส่วนใดทำงานจริงและส่วนใดจำลอง อย่าอ้างว่ามีความสามารถที่ยังไม่ได้สร้างหรือทดสอบ

ผลที่ต้องได้: MVP ที่ทดสอบสมมติฐานได้ และบอกข้อจำกัดตรงไปตรงมา

เริ่ม STEP 8: เตรียมสรุปสำหรับ Startup Contest โดยใช้ข้อมูลที่เรายืนยันแล้วเท่านั้น ครอบคลุม (1) ผลิตภัณฑ์ช่วยใครและทำอะไร (2) ปัญหาและหลักฐาน (3) สถานะ Keep/Improve/Pivot/Re-test และสิ่งที่ปรับ (4) Lean Canvas ล่าสุดครบ 9 Block (5) MVP/Prototype และสิ่งที่ทดสอบแล้ว (6) รูปแบบรายได้ ช่องทาง ต้นทุน (7) ความเสี่ยงที่ยังเหลือ (8) แผนถัดไปและสิ่งที่ต้องการจากกรรมการ แยกผลทดสอบจริงออกจากแผนทดสอบและสมมติฐาน ห้ามแต่งขนาดตลาด รายได้ หรือผลตอบรับลูกค้า หากมีคำถามที่ยังตอบไม่ได้ ให้บอกตรง ๆ พร้อมแผนหาคำตอบ ปิดท้ายด้วยคำถามยาก 5 ข้อที่กรรมการอาจถาม และแนวทางตอบที่ซื่อสัตย์ รวมถึง 3 ขั้นตอนถัดไปที่ทีมทำได้จริง

ผลที่ต้องได้: เรื่องนำเสนอที่ไม่กล่าวอ้างเกินหลักฐานและพร้อมตอบคำถามกรรมการ

นำไปเผยแพร่ใน Google Sites

ไฟล์ HTML นี้เป็นไฟล์ต้นฉบับ — Google Sites ไม่ได้ทำหน้าที่เป็นพื้นที่โฮสต์ไฟล์ HTML โดยตรงทุกกรณี

↗
วิธีแนะนำสำหรับไฟล์นี้: โฮสต์ไฟล์ก่อน แล้วฝังด้วย URL

หน้าเว็บมี CSS และ JavaScript สำหรับปุ่มคัดลอกและการทำงานบนหน้า การฝังโค้ดโดยตรงอาจต้องปรับขนาดหรือรูปแบบการวางโค้ดใน Embed frame ให้ทดสอบ Preview ก่อน Publish

เตรียมไฟล์ HTML

ดาวน์โหลดไฟล์นี้ แล้วเปลี่ยนชื่อให้จำง่าย เช่น lean-canvas-coach.html ตรวจเปิดในเบราว์เซอร์ก่อนอัปโหลด

โฮสต์ไฟล์บนเว็บที่เปิดสาธารณะ

อัปโหลดไฟล์ไปยังบริการโฮสต์ Static Site เช่น GitHub Pages หรือบริการโฮสต์เว็บที่โรงเรียนอนุมัติ แล้วเปิด URL ที่ได้เพื่อตรวจว่าเว็บเข้าถึงได้โดยไม่ต้องล็อกอิน

ฝังหน้าเว็บใน Google Sites

เปิด Google Sites ในโหมดแก้ไข → เลือก Insert (แทรก) → Embed (ฝัง) → By URL (ตาม URL) → วาง URL เว็บไซต์ที่โฮสต์ → Insert

ปรับขนาดและเผยแพร่

ลากขอบกรอบฝังให้กว้างและสูงพอ → ใช้ Preview ตรวจบน Desktop และมือถือ → กด Publish (เผยแพร่) แล้วเปิด URL เว็บไซต์จริงทดสอบปุ่มคัดลอกและทุกส่วนอีกครั้ง

+

ต้องการวางโค้ดตรงใน Google Sites?

เหมาะกับ Snippet หรือส่วนประกอบเฉพาะ ไม่ใช่วิธีที่แนะนำสำหรับไฟล์เต็ม

  1. ในหน้าแก้ไข Google Sites เลือก Insert → Embed → Embed code
  2. วาง HTML snippet ที่ต้องการฝัง โดย CSS อยู่ในแท็ก <style>...</style> และ JavaScript อยู่ใน <script>...</script>
  3. กด Next → Insert ปรับขนาดกรอบ แล้ว Preview ก่อน Publish

สำหรับไฟล์นี้ไม่ควรวางเอกสาร HTML ทั้งชุดพร้อม <!doctype html>, <head> และ <body> ลงไปโดยไม่ทดสอบ เพราะช่องฝังโค้ดอาจต้องใช้เฉพาะส่วนที่ฝังได้ และแสดงผลภายในกรอบ (iframe) หากมีปัญหาให้ใช้วิธีโฮสต์ URL ด้านบน
